# MHGU Blender Importer

<img width="2047" height="1011" alt="345820dd-9ece-4f7e-ad40-4063fb88096c" src="https://github.com/user-attachments/assets/45756a2e-d5aa-4acb-bf11-1088faaae2b2" />
This is a Blender add-on used for importing `.mod` model files and `.lmt` animation files from Monster Hunter Generations Ultimate (MHGU / MHXX), supporting monsters, characters, weapons, stages, villages, and props.

## Notes
1. The testing platform for this add-on is **Blender 3.6.13**. Compatibility with other versions has not been tested, but it should work in theory.
2. Before using this add-on, you must refer to Handburger's tutorials to unpack the MHGU model files and convert the `.tex` texture files into `.png` format.
3. Place the converted `.png` texture files (and the companion `.mrl` material file, especially for stage/village/prop models) in the same folder as the `.mod` file so the add-on can automatically resolve and link textures. Otherwise, a temporary pink material placeholder will be displayed.
4. You need to import the `.mod` model file first before importing the `.lmt` animation file.
5. It is highly recommended not to perform non-one-to-one imports of models, armatures, and animations, as potential issues have not been tested (it is suggested to process one model per Blender project).

---

## Instructions
1. Open Blender and create a new project.
2. Install the **MHGU-blenderImporter** add-on.
3. Menu Bar: `File -> Import -> MHGU Model (.mod)`. Select the `.mod` model to import into Blender. The add-on will automatically complete the armature generation and binding, material correction, vertex color/alpha layer setup, and texture information importing.
4. Menu Bar: `File -> Import -> MHGU Animation (.lmt)`. Select the `.lmt` animation to import into Blender. If the model only has one set of armatures, the animation import will be completed automatically.

## Format Specification
*(The following content is generated by Google Gemini)*

### 1. Model File Structure (.MOD)
Based on `version = 212` (Switch version of MHGU). The file structure is strictly stored in little-endian format.

#### 1.1 File Header Area
The main header defines the counts and absolute byte offsets of all data blocks, followed by bounding-box vectors at `0x50` (`bbmin`) and `0x60` (`bbmax`).

| Offset | Length | Type | Field Name | Description |
|---|---|---|---|---|
| `0x00` | 4 | Char Array | Magic | File identifier, fixed as `MOD\x00` |
| `0x04` | 1 | uint8 | Version | Major version number (usually `212` / `0xD4` for MHGU) |
| `0x05` | 1 | uint8 | Version2 | Minor version flag |
| `0x06` | 2 | uint16 | BoneCount | Total number of bones included in the model (`0` for static stages/props) |
| `0x08` | 2 | uint16 | MeshCount | Total number of meshes included in the model |
| `0x0A` | 2 | uint16 | MaterialCount | Total number of materials |
| `0x0C` | 4 | uint32 | VertexCount | Total global vertex count |
| `0x10` | 4 | uint32 | FaceCount | Total global face count (i.e., number of strip indices) |
| `0x14` | 4 | uint32 | VertexIds | Total number of edges or vertex IDs |
| `0x18` | 4 | uint32 | VtxBufSize | Total byte size of the primary vertex buffer |
| `0x1C` | 4 | uint32 | SecBufSize | Total byte size of the secondary buffer |
| `0x20` | 4 | uint32 | GroupCount | Total number of nodes or groups |
| `0x24` | 4 | uint32 | BonesOffset | Absolute offset to the **Bones Data Area** |
| `0x28` | 4 | uint32 | GroupOffset | Absolute offset to the **Groups Data Area** |
| `0x2C` | 4 | uint32 | TexOffset | Absolute offset to the **Material Names Area** (128-byte fixed strings) |
| `0x30` | 4 | uint32 | MeshOffset | Absolute offset to the **Mesh Headers Area** |
| `0x34` | 4 | uint32 | VtxOffset | Absolute offset to the **Vertex Buffer Area** |
| `0x38` | 4 | uint32 | FacesOffset | Absolute offset to the **Face Indices Area** |
| `0x3C` | 4 | uint32 | UnkOffset | Absolute offset to trailing data |

#### 1.2 Bones Data Area
Located at the absolute offset pointed to by `BonesOffset` (present when `BoneCount > 0`), containing four continuous data blocks:

1. **Basic Bone Information**
   - Each bone occupies 24 bytes (Total: `BoneCount * 24` bytes).
   - `0x00`: Bone ID (uint8)
   - `0x01`: Parent Bone ID (uint8). `255` indicates this bone is a root node with no parent.
   - `0x02`: Child Bone ID (uint8)
   - `0x03`: State flags or reserved bits (uint8)
2. **Local Transform Matrices**
   - Immediately following the basic bone information. Each bone occupies 64 bytes (Total: `BoneCount * 64` bytes).
   - The data is a 4x4 single-precision float matrix, column-major.
3. **Absolute Transform Matrices**
   - Immediately following the local matrices. Each bone also occupies 64 bytes.
   - **Core Design Detail**: For newer model versions (`Version >= 190`) with bones (`BoneCount > 0`), the **global vertex scaling ratio and offset** for `int16` quantized vertices are stored in Bone 0's matrices: the scale is the column vector length of Bone 0's absolute matrix (`amat`), and the offset is `amat.translation + lmat.translation`.
4. **Animation Bone Remap Table**
   - Immediately following the absolute matrices, the length is **fixed at 256 bytes**.
   - **Crucial Pitfall**: This is a lookup table used to map external animation tracks to the internal bone IDs. **It must NEVER be used as the bone mapping table for mesh vertices.** If mixed up in the code, it will cause vertex weights to be lost, resulting in catastrophic bugs like "meshes flying around" or "shattering in mid-air" when playing animations.

#### 1.3 Mesh Data Area
Located at `MeshOffset`. Each Mesh Header (`MODMeshPartv2`) is **48 bytes** long.

| Offset | Type | Field Name | Description |
|---|---|---|---|
| `0x01` | uint8 | MeshType | Mesh type or rendering mode, e.g., visibility identifier. |
| `0x02` | uint16 | VertexCount | Number of vertices controlled by this mesh. |
| `0x05` | uint16 | MaterialIdx | **12-bit Material ID**, extracted via `uint16 >> 4` (bits 4..15 at `0x05-0x06`). Reading only 1 byte (`uint8 >> 4`) truncates material indices `>= 16` on large stage/village models. |
| `0x08` | uint8 | SingleBone | **Single Bone Fallback ID**. When a mesh is a rigid geometry without per-vertex weights, all vertices are bound to this global bone by default. |
| `0x09` | uint8 | RenderPriority | **Render Layer / Draw Priority** (`0` for base opaque geometry, `1..255` for layered alpha/decal passes). Used on static stages to apply a micro surface-normal offset to coplanar terrain decal layers and prevent Z-fighting. |
| `0x0A` | uint8 | Stride | **Vertex Stride** (number of bytes each vertex occupies). |
| `0x0B` | uint8 | BlockType | Legacy 1-byte vertex block flag (low 8 bits of `BlockHash`). |
| `0x0C` | uint32 | VertexSub | Base vertex index offset subtracted from triangle strip indices (`index - VertexSub`). |
| `0x10` | uint32 | VtxOffsetAdd | Byte offset relative to `VtxOffset`. |
| `0x14` | uint32 | BlockHash | **32-bit Vertex Declaration Hash**. Its upper 20-bit prefix (`BlockHash >> 12`) uniquely identifies the exact vertex format across all 50+ MT Framework vertex declarations. |
| `0x18` | uint32 | FaceOffset | Relative starting index of face strip data (multiply by 2 bytes and add `FacesOffset`). |
| `0x1C` | uint32 | FaceCount | Number of `uint16` triangle-strip indices for this mesh (`0xFFFF` acts as primitive restart). |
| `0x24` | uint8 | BoneMapIdx | Index for the local vertex-to-bone mapping table. Mostly deprecated in Switch formats. |

#### 1.4 Vertex Buffer Area
Absolute offset calculation formula: `VtxOffset + VtxOffsetAdd + (Stride * VertexSub)`.

Unlike guessing layouts from `Stride` and the 1-byte `BlockType` alone, MT Framework defines each vertex format by its 32-bit `BlockHash` (`BlockHash >> 12`), which divides vertices into two primary families:

##### Family 1: Static / Scene / Prop `float32` Formats (`BlockHash >> 12` in `0xa7d7d`, `0x207d6`, `0x49b4f`, `0x926fd`, `0xd8297`, etc.)
*Used for stages, villages, weapon props, and unrigged meshes (as well as rigged tail props using `float32` positions)*
- **Positions (`0x00-0x0C`)**: Stored directly as **3x IEEE-754 single-precision floats (`<fff`)** in model space (no `int16` dequantization).
- **Normals & Tangents**: 4-byte packed normal at `0x0C-0x10` (and optional 4-byte tangent at `0x10-0x14` for normal-mapped formats such as `0x49b4f`, `0x926fd`, `0xd8297`).
- **UVs**: Half-precision float (`<HH`) or single-precision float (`<ff`) UV1 (and optional UV2 for lightmapped/multi-UV formats).
- **Vertex Color & Vertex Alpha (`PaintedModel*` formats such as `0x207d6`, `0x49b4f`, `0x926fd`, `0xa14e0`, `0xb6681`, `0xc9690`)**:
  - 4 bytes (`<BBBB`) of `RGBA` vertex color (`0..255`).
  - **Terrain Blending vs. Foliage Cutouts**: In MHGU stage models, multi-texture terrain transitions (e.g., grass-to-rock or riverbank-to-sand) are built using coplanar overlay meshes with `XfBAW_1__...` materials whose DXT1 textures are fully opaque (`Texture Alpha = 1.0`), relying on **Vertex Alpha (`255 -> 0`)** to feather the outer boundary smoothly. Conversely, trees and bushes have constant `Vertex Alpha = 255` and rely on texture alpha cutouts. Multiplying `Texture Alpha * Vertex Alpha` and selecting `BLEND` (for vertex-alpha gradients) vs. `CLIP` (for cutout foliage) accurately reproduces both smooth ground transitions and front-to-back tree depth sorting.

##### Family 2: Skinned `int16` Formats (`BlockHash >> 12` in `0x14d40`, `0x64593`, `0xb3921`, `0xc31f2`, `0xa8fab`, `0x0cb68`, `0xbb424`, etc.)
*Used for monsters, characters, and deformable meshes*
- **Positions (`0x00-0x06`)**: Stored as **3x 16-bit signed short integers (`<hhh`)**, restored via `Coordinate / 32767.0 * Global Scale + Offset`.
- **Specialized Skinning Layouts**:
  - **4-Bone Standard Formats (`0x14d40`, `0xbde53`, `0x77d87`, `0xd86ca`, `0xda55a`, `0x64593`, `0xcc510`, Stride 28/32/40/44)**:
    - `0x06-0x08`: Weight 1 (`int16 / 32767.0`)
    - `0x10-0x14`: Bone IDs 1 to 4 (`4x uint8`)
    - `0x14-0x18`: UV1 (`2x half-float`) and `0x18-0x1C`: Weight 2 & Weight 3 (`2x half-float`, swapped in `0xcc510`), with `Weight 4 = 1.0 - W1 - W2 - W3`.
  - **2-Bone Half-Float Bone ID Formats (`0xc31f2`, `0x6a2e1`, `0xa0135`, `0x0d9e8` at Stride 24/28; `0xb3921`, `0x1b9a2` at Stride 36/40)**:
    - `0x06-0x08`: Weight 1 (`int16 / 32767.0`), `Weight 2 = 1.0 - W1`.
    - Bone IDs 1 and 2 are stored as **IEEE-754 half-precision floats** (at `0x14-0x18` for Stride 24/28, or `0x10-0x14` for Stride 36/40) and must be decoded to float first before casting to integer bone indices.
  - **1-Bone Compact Formats (`0xb0983` Stride 12, `0xa8fab` / `0x01cb8` Stride 20, `0x667b1` / `0xc9cfc` Stride 24, `0xd8778` Stride 32, `0x707fb` Stride 36)**:
    - `0x06-0x08`: **Local Bone ID (`uint16`)** tucked immediately after the `int16` XYZ coordinates, with a fixed weight of `1.0`.
  - **8-Bone Formats (`0xbb424`, `0x12737`, `0x75c3e`, `0xd84e3`, `0xcbcf7`, Stride 36/40)**:
    - `0x06-0x08`: Weight 1 (`int16 / 32767.0`), `0x0C-0x10`: Weights 2..5 (`4x uint8 / 255.0`), `0x10-0x18`: Bone IDs 1..8 (`8x uint8`), `0x18-0x1C`: UV1 (`2x half-float`), `0x1C-0x20`: Weights 6..7 (`2x half-float`), and `Weight 8 = 1.0 - sum(W1..W7)`.

#### 1.5 Companion Material Library (.MRL) Resolution
For stages, villages, and complex models where multiple materials reference shared environment textures rather than `{model_name}_BM`, the texture bindings are stored in the companion `.mrl` (`MRL\x00` v34) file:
- Each material name in `.mod` is hashed using **JamCRC** (`(~zlib.crc32(name.encode('ascii'))) & 0xFFFFFFFF`) and matched against the 60-byte material headers in `.mrl` (`offset + 4`).
- The material's 12-byte GPU command stream binds 1-based texture indices (when `word0 & 0xFF == 0xC3`) into the `.mrl` texture table (76 bytes per entry), automatically resolving diffuse (`_BM` / `_DM`), normal (`_NM`), and mask (`_MM`) textures.

### 2. Animation File Structure (.LMT)
This file is the crucial data managing skeletal animations.

#### 2.1 File Header Area
- `0x00` - `0x03`: File identifier, fixed as `LMT\x00`.
- `0x04` - `0x05`: Animation file version number.
- `0x06` - `0x07`: Total number of actions included.
- Starting from `0x08`: An array of unsigned 32-bit integers, storing the absolute file offset for each action's Anim Header.

#### 2.2 Anim Header (Action Info)
Located at the offset address calculated above.
- `0x00` - `0x03`: Starting offset for all "animation track" data included in this action.
- `0x04` - `0x07`: Total number of tracks (usually 256, corresponding to the 256-byte lookup table in the model file).
- `0x08` - `0x0B`: Total number of frames for this action.
- `0x0C` - `0x0F`: Starting frame of the animation loop, often used for looping gaits.

#### 2.3 Animation Tracks
Each track corresponds to a virtual bone ID (mapped to a real bone via the 256-byte remap table in the `.mod` file; for `LMT version > 90`, each track header is 40 bytes with the bone ID at `0x24`, otherwise 36 bytes).
Each track header specifies its buffer compression type (`BufType`), transform usage (rotation, translation, or scale), byte size, data offset, reference value, and optional quantization `Bounds` (`extent` and `base` vectors).

#### 2.4 Keyframe Buffer Decompression
The underlying engine uses highly complex floating-point difference and compression algorithms:
- **Extreme Value Limits**: The buffer bounds declare the scale (`extent`) and offset (`base`) for X, Y, Z, W components of that track.
- **Bit-Width Encoding**: Time frame deltas (`relframe`) and quantized quaternion/vector components are packed into 4-byte, 5-byte, 6-byte, 8-byte, or 12-byte structures (`BufType` 1, 4, 5, 6, 7, 11..15).
- **Restoring Interpolation**: The extracted integers are normalized and linearly interpolated with `extent` and `base` to restore high-precision quaternions or spatial coordinates.

## 格式说明
*(以下内容由 Google Gemini 生成)*

### 1. 模型文件结构 (.MOD)
以 `version = 212` (Switch 版 MHGU) 为基准。文件结构严格按照小端序存储。

#### 1.1 文件头部区
文件主头部定义了各数据块的数量与绝对偏移地址，并在 `0x50`（`bbmin`）与 `0x60`（`bbmax`）处存放模型包围盒向量。

| 偏移量 | 长度 | 类型 | 字段名称 | 描述 |
|---|---|---|---|---|
| `0x00` | 4 | 字符数组 | Magic | 文件标识符，固定为 `MOD\x00` |
| `0x04` | 1 | 无符号8位整数 | Version | 主版本号 (MHGU 通常为 `212` / `0xD4`) |
| `0x05` | 1 | 无符号8位整数 | Version2 | 次版本标识 |
| `0x06` | 2 | 无符号16位整数 | BoneCount | 模型包含的骨骼总数（静态场景/道具模型为 `0`） |
| `0x08` | 2 | 无符号16位整数 | MeshCount | 模型包含的网格总数 |
| `0x0A` | 2 | 无符号16位整数 | MaterialCount| 材质总数 |
| `0x0C` | 4 | 无符号32位整数 | VertexCount | 全局顶点总数 |
| `0x10` | 4 | 无符号32位整数 | FaceCount | 全局面索引总数 (即三角带索引数) |
| `0x14` | 4 | 无符号32位整数 | VertexIds | 边界或顶点 ID 总数 |
| `0x18` | 4 | 无符号32位整数 | VtxBufSize | 主顶点缓冲区总字节大小 |
| `0x1C` | 4 | 无符号32位整数 | SecBufSize | 第二缓冲区字节大小 |
| `0x20` | 4 | 无符号32位整数 | GroupCount | 节点或组总数 |
| `0x24` | 4 | 无符号32位整数 | BonesOffset | **骨骼数据区**的绝对偏移 |
| `0x28` | 4 | 无符号32位整数 | GroupOffset | **组数据区**的绝对偏移 |
| `0x2C` | 4 | 无符号32位整数 | TexOffset | **材质名称区**的绝对偏移（每个材质名占 128 字节定长字符串） |
| `0x30` | 4 | 无符号32位整数 | MeshOffset | **网格头部区**的绝对偏移 |
| `0x34` | 4 | 无符号32位整数 | VtxOffset | **顶点缓冲区**的绝对偏移 |
| `0x38` | 4 | 无符号32位整数 | FacesOffset | **面索引区**的绝对偏移 |
| `0x3C` | 4 | 无符号32位整数 | UnkOffset | 尾部附加数据偏移 |

#### 1.2 骨骼数据区
位于由骨骼区绝对偏移所指向的位置（当 `BoneCount > 0` 时存在），包含四部分连续的数据块：

1. **骨骼基础信息**
   - 每个骨骼占 24 字节（总计 骨骼数 × 24 字节）。
   - `0x00`: 骨骼编号 (无符号8位整数)
   - `0x01`: 父骨骼编号 (无符号8位整数)，`255` 表示该骨骼为根节点，无父级。
   - `0x02`: 子骨骼编号 (无符号8位整数)
   - `0x03`: 状态标志或保留位 (无符号8位整数)
2. **局部变换矩阵**
   - 紧跟在骨骼基础信息之后。每个骨骼占 64 字节（总计 骨骼数 × 64 字节）。
   - 数据为 4x4 单精度浮点矩阵，列主序。
3. **绝对变换矩阵**
   - 紧跟在局部矩阵之后。每个骨骼同样占 64 字节。
   - **核心设计细节**：对于较新的模型版本（`Version >= 190`）且带骨骼的模型（`BoneCount > 0`），`int16` 量化顶点的**全局缩放比例与偏移量**隐藏在第 0 号骨骼矩阵中：提取第 0 号骨骼绝对矩阵前三列的向量长度即为缩放倍率，绝对矩阵与局部矩阵的平移向量之和即为全局偏移。
4. **动画骨骼映射表**
   - 紧跟在绝对矩阵后，长度**固定为 256 字节**。
   - **极易犯错的避坑点**：这是用来将外部动画轨道映射到本体骨骼编号上的对照表，**绝对不能将其当作网格顶点的骨骼映射表**。在代码中如果混用，将导致顶点权重丢失，并在播放动画时发生“网格乱飞”、“碎裂在半空中”的毁灭性错误。

#### 1.3 网格数据区
位于网格绝对偏移处。每个网格头部（`MODMeshPartv2`）长度为 **48 字节**。

| 偏移量 | 类型 | 字段名称 | 描述 |
|---|---|---|---|
| `0x01` | 无符号8位整数 | MeshType | 网格类型或渲染模式，如可见性标识。 |
| `0x02` | 无符号16位整数 | VertexCount | 此网格控制的顶点数量。 |
| `0x05` | 无符号16位整数 | MaterialIdx | **12位材质编号**，存储在 `0x05-0x06` 的高 12 位（需以 `uint16 >> 4` 取值）。若仅按单字节 `uint8 >> 4` 读取，会导致材质数超过 16 个的大型场景/村庄模型材质索引截断错乱。 |
| `0x08` | 无符号8位整数 | SingleBone | **单骨骼回退编号**。当网格为无逐顶点权重的刚体几何体时，所有顶点默认绑定到此全局骨骼。 |
| `0x09` | 无符号8位整数 | RenderPriority | **渲染层级优先级**（`0` 为底层不透明地形/几何体，`1..255` 为多层透明/贴花叠加层）。在静态场景中用于对共面重合的地形过渡贴花施加微距表面法线偏移，从而消除 Blender 视口中的共面闪烁（Z-Fighting）。 |
| `0x0A` | 无符号8位整数 | Stride | **顶点步长** (每个顶点占用的字节数)。 |
| `0x0B` | 无符号8位整数 | BlockType | 旧版 1 字节顶点块标识（即 `BlockHash` 的低 8 位）。 |
| `0x0C` | 无符号32位整数 | VertexSub | 顶点基址偏移值（面索引需减去 `VertexSub` 才是当前网格内的局部顶点索引）。 |
| `0x10` | 无符号32位整数 | VtxOffsetAdd| 相对 `VtxOffset` 的字节偏移量。 |
| `0x14` | 无符号32位整数 | BlockHash | **32位顶点声明哈希**。其高 20 位前缀（`BlockHash >> 12`）唯一标识 MT Framework 中 50 余种具体的顶点数据排列结构。 |
| `0x18` | 无符号32位整数 | FaceOffset | 面索引数据的相对起始位置 (读取时需乘以 2 字节并加上 `FacesOffset`)。 |
| `0x1C` | 无符号32位整数 | FaceCount | 该网格的 `uint16` 三角带面索引数量（`0xFFFF` 为图元重启标识）。 |
| `0x24` | 无符号8位整数 | BoneMapIdx | 局部顶点骨骼映射表的索引。在 Switch 等压缩格式中多废弃不用。 |

#### 1.4 顶点缓冲区
绝对偏移计算公式：`VtxOffset + VtxOffsetAdd + (Stride * VertexSub)`。

MT Framework 并非仅靠 `Stride`（步长）和 1 字节 `BlockType` 来区分顶点格式，而是通过 32 位 `BlockHash` 的高 20 位前缀（`BlockHash >> 12`）精确定义每个顶点的内部字段布局，主要分为两大格式族：

##### 格式族一：静态 / 场景 / 道具 `float32` 顶点格式（`BlockHash >> 12` 为 `0xa7d7d`、`0x207d6`、`0x49b4f`、`0x926fd`、`0xd8297` 等）
*用于地图场景、村庄、武器、采集物以及使用浮点坐标的断尾等静态网格*
- **顶点坐标 (`0x00-0x0C`)**: 直接存储为 **3 个 IEEE-754 单精度浮点数 (`<fff`)**，处于原始模型空间，无需进行 `int16` 反量化缩放。
- **法线与切线**: `0x0C-0x10` 为 4 字节压缩法线（带法线贴图的格式如 `0x49b4f`、`0x926fd`、`0xd8297` 在 `0x10-0x14` 额外包含 4 字节切线）。
- **UV 坐标**: 半精度浮点 (`<HH`) 或单精度浮点 (`<ff`) 存储的 UV1（以及多重贴图格式下的 UV2）。
- **顶点色与顶点 Alpha 透明遮罩（`PaintedModel*` 格式，如 `0x207d6`、`0x49b4f`、`0x926fd`、`0xa14e0`、`0xb6681`、`0xc9690`）**:
  - 顶点末尾包含 4 字节 (`<BBBB`) 的 `RGBA` 顶点色（取值 `0..255`）。
  - **地面无缝过渡与树木镂空机制**: 在 MHGU 场景模型中，不同地形材质（如草地、河滩碎石、岩壁）的交界处会铺设一层与地面完全共面的过渡网格（材质名带 `XfBAW_1__...`），其绑定的地面贴图本身是不透明的 DXT1 贴图（`贴图 Alpha = 1.0`），依靠**顶点 Alpha（中心 `255` 向外圈边界渐变为 `0`）**实现平滑羽化过渡；而树木、灌木、花草等植被网格的顶点 Alpha 恒为 `255`，依靠贴图自身的透明通道进行镂空。插件通过将 `贴图 Alpha × 顶点 Alpha` 相乘，并自动为顶点 Alpha 渐变层启用 `BLEND`（平滑混合）、为植被镂空层启用 `CLIP`（Alpha 钳制以保证正确的深度前后遮挡关系），即可完整还原原版场景效果。

##### 格式族二：骨骼蒙皮 `int16` 顶点格式（`BlockHash >> 12` 为 `0x14d40`、`0x64593`、`0xb3921`、`0xc31f2`、`0xa8fab`、`0x0cb68`、`0xbb424` 等）
*用于怪物本体、角色及精细形变部位*
- **顶点坐标 (`0x00-0x06`)**: 存储为 **3 个 16 位有符号短整数 (`<hhh`)**，解析时需执行 `坐标值 / 32767.0 × 全局缩放 + 偏移量` 还原。
- **典型蒙皮步长与骨骼权重布局剖析**:
  - **4 骨骼多权重标准格式 (`0x14d40`、`0xbde53`、`0x77d87`、`0xd86ca`、`0xda55a`、`0x64593`、`0xcc510`，步长 28/32/40/44)**:
    - `0x06-0x08`: 权重 1 (`int16 / 32767.0`)
    - `0x10-0x14`: 骨骼编号 1 至 4 (`4x uint8`)
    - `0x14-0x18`: UV1 坐标 (`2x half-float`)，`0x18-0x1C`: 权重 2 与权重 3 (`2x half-float`，在 `0xcc510` 中与 UV1 位置互换)，权重 4 由 `1.0 - W1 - W2 - W3` 计算得出。
  - **2 骨骼半精度浮点骨骼索引格式 (`0xc31f2`、`0x6a2e1`、`0xa0135`、`0x0d9e8` 步长 24/28；`0xb3921`、`0x1b9a2` 步长 36/40)**:
    - `0x06-0x08`: 权重 1 (`int16 / 32767.0`)，权重 2 为 `1.0 - W1`。
    - **骨骼编号 1 与 2 存储为半精度浮点数 (`half-float`)**（步长 24/28 位于 `0x14-0x18`，步长 36/40 位于 `0x10-0x14`），必须先按 IEEE-754 半精度浮点解压后再转为整数骨骼编号。
  - **单骨骼紧凑压缩格式 (`0xb0983` 步长 12，`0xa8fab` / `0x01cb8` 步长 20，`0x667b1` / `0xc9cfc` 步长 24，`0xd8778` 步长 32，`0x707fb` 步长 36，如钢龙躯干鳞片)**:
    - 该格式抛弃了权重，每个顶点仅受唯一一根骨骼控制（权重固定为 `1.0`）。
    - `0x06-0x08`（紧跟在 `int16` XYZ 坐标之后的第 7、8 字节）：直接存放**局部骨骼编号 (`uint16`)**。
  - **8 骨骼高阶蒙皮格式 (`0xbb424`、`0x12737`、`0x75c3e`、`0xd84e3`、`0xcbcf7`，步长 36/40)**:
    - `0x06-0x08`: 权重 1 (`int16 / 32767.0`)，`0x0C-0x10`: 权重 2..5 (`4x uint8 / 255.0`)，`0x10-0x18`: 骨骼编号 1..8 (`8x uint8`)，`0x18-0x1C`: UV1 (`2x half-float`)，`0x1C-0x20`: 权重 6..7 (`2x half-float`)，权重 8 为 `1.0 - sum(W1..W7)`。

#### 1.5 配套材质库文件 (.MRL) 贴图解析
对于地图场景、村庄等包含数十个材质球且贴图名不以 `{模型名}_BM` 命名的模型，材质与贴图的绑定关系存放在同目录同名的 `.mrl`（`MRL\x00` v34）文件中：
- `.mod` 中的每个材质名称通过 **JamCRC** 算法（即对标准 CRC32 按位取反：`(~zlib.crc32(name.encode('ascii'))) & 0xFFFFFFFF`）计算 32 位哈希，与 `.mrl` 中的 60 字节材质头（偏移 `+4` 处）进行匹配。
- 材质指向的 12 字节属性指令流中，当指令字满足 `word0 & 0xFF == 0xC3` 时，`word1` 即为 `.mrl` 贴图路径表（每项 76 字节）中的 1 起始贴图索引，从而自动解析出该材质绑定的漫反射贴图（`_BM` / `_DM`）、法线贴图（`_NM`）与遮罩贴图（`_MM`）。

### 2. 动画文件结构 (.LMT)
该文件是管理骨骼动画的关键数据。

#### 2.1 文件头部区
- `0x00` - `0x03`: 文件标识符，固定为 `LMT\x00`。
- `0x04` - `0x05`: 动画文件版本号。
- `0x06` - `0x07`: 包含的动作数量。
- `0x08` 开始: 一组无符号32位整数数组，存放着每一个动作信息头的绝对文件偏移量。

#### 2.2 动作信息头
位于上述计算得出的偏移地址。
- `0x00` - `0x03`: 此动作包含的所有“动画轨道”数据起始偏移。
- `0x04` - `0x07`: 轨道总数（对应模型文件中 256 字节的骨骼映射表）。
- `0x08` - `0x0B`: 此动作的总帧数。
- `0x0C` - `0x0F`: 动画循环的起始帧，常用于循环步态。

#### 2.3 动画轨道
每一个轨道对应一个虚拟的骨骼编号（需通过 `.mod` 模型里的 256 字节对照表映射到真实骨骼；当 `LMT 版本号 > 90` 时每条轨道头占 40 字节且骨骼编号位于 `0x24`，否则占 36 字节）。
轨道头内部定义了缓冲压缩类型（`BufType`）、变换通道类型（旋转、平移或缩放）、缓冲区字节大小、数据区绝对偏移、初始参考值以及可选的极值包围盒偏移（`Bounds`，包含 `extent` 缩放跨度与 `base` 基准偏移）。

#### 2.4 关键帧缓冲解压
底层引擎使用了高度复杂的浮点数差分和压缩算法：
- **极值限制**: 缓冲区极值块声明了该段动作在 X, Y, Z, W 分量上的跨度（`extent`）与基准偏移（`base`）。
- **位宽编码**: 时间帧增量（`relframe`）与量化后的旋转四元数/平移向量根据压缩类型（`BufType` 1, 4, 5, 6, 7, 11..15）被紧凑打包为 4、5、6、8 或 12 字节结构。
- **还原插值**: 提取出的量化整数归一化后作为插值因子，结合 `extent` 与 `base` 进行线性映射计算，最终还原出高精度的四元数或空间坐标。

# MHGU Blender Importer

This is a Blender add-on used for importing `.mod` model files and `.lmt` animation files from Monster Hunter Generations Ultimate (MHGU / MHXX).

---

## Acknowledgements
* Thanks to **Handburger** for creating the **SaladSoftware** tools and writing the MHGU model and material modification tutorials. Before using this add-on, you must refer to Handburger's tutorials to unpack the MHGU model files and convert the `.tex` texture files into `.png` format.
* Thanks to **Lukas Cone** for creating the **MT Framework tools**. Most features in this add-on reference that tool. If you edit models using 3DS MAX instead of Blender, it is recommended to use the original MT Framework tools.
* This add-on was completed with the full assistance of **Google Antigravity**. Code comments may contain Chinese. Thanks to Google.

---

## Notes
1. The testing platform for this add-on is **Blender 3.6.13**. Compatibility with other versions has not been tested, but it should work in theory.
2. Before using this add-on, you must refer to Handburger's tutorials to unpack the MHGU model files and convert the `.tex` texture files into `.png` format.
3. If you do not place the `.png` texture files with the same name in the same folder as the `.mod` file, a temporary pink material will be used as a placeholder by default.
4. You need to import the `.mod` model file first before importing the `.lmt` animation file.
5. It is highly recommended not to perform non-one-to-one imports of models, armatures, and animations, as potential issues have not been tested (it is suggested to process one monster per Blender project).

---

## Instructions
1. Open Blender and create a new project.
2. Install the **MHGU-blenderImporter** add-on.
3. Menu Bar: `File -> Import -> MHGU Model (.mod)`. Select the `.mod` model to import into Blender. The add-on will automatically complete the armature generation and binding, material correction, and texture information importing.
4. Menu Bar: `File -> Import -> MHGU Animation (.lmt)`. Select the `.lmt` animation to import into Blender. If the model only has one set of armatures, the animation import will be completed automatically.

## Format Specification
*(The following content is generated by Google Gemini)*

### 1. Model File Structure (.MOD)
Based on `version = 237` (Switch version of MHGU). The file structure is strictly stored in little-endian format.

#### 1.1 File Header Area
The total length is fixed at 64 bytes, defining the locations and counts of various data blocks.

| Offset | Length | Type | Field Name | Description |
|---|---|---|---|---|
| `0x00` | 4 | Char Array | Magic | File identifier, fixed as `MOD\x00` |
| `0x04` | 2 | uint16 | Version | Major version number (usually 237 for MHGU) |
| `0x06` | 2 | uint16 | Version2 | Minor version number |
| `0x08` | 4 | uint32 | BoneCount | Total number of bones included in the model |
| `0x0C` | 4 | uint32 | MeshCount | Total number of meshes included in the model |
| `0x10` | 4 | uint32 | MaterialCount | Total number of materials |
| `0x14` | 4 | uint32 | VertexCount | Total global vertex count |
| `0x18` | 4 | uint32 | FaceCount | Total global face count (i.e., number of indices) |
| `0x1C` | 4 | uint32 | EdgeCount | Total number of edges or wireframes |
| `0x20` | 4 | uint32 | GroupCount | Total number of nodes or groups |
| `0x24` | 4 | uint32 | BonesOffset | Absolute offset to the **Bones Data Area** |
| `0x28` | 4 | uint32 | GroupOffset | Absolute offset to the **Groups Data Area** |
| `0x2C` | 4 | uint32 | TexOffset | Absolute offset to the **Texture Names & Resources Area** |
| `0x30` | 4 | uint32 | MeshOffset | Absolute offset to the **Mesh Headers Area** |
| `0x34` | 4 | uint32 | VtxOffset | Absolute offset to the **Vertex Buffer Area** |
| `0x38` | 4 | uint32 | FacesOffset | Absolute offset to the **Face Indices Area** |
| `0x3C` | 4 | uint32 | UnkOffset | Absolute offset to unknown data or bounding box data |

#### 1.2 Bones Data Area
Located at the absolute offset pointed to by `BonesOffset`, containing three continuous data blocks:

1. **Basic Bone Information**
   - Each bone occupies 24 bytes (Total: `BoneCount * 24` bytes).
   - `0x00`: Bone ID (uint8)
   - `0x01`: Parent Bone ID (uint8). `255` indicates this bone is a root node with no parent.
   - `0x02`: Child Bone ID (uint8)
   - `0x03`: State flags or reserved bits (uint8)
2. **Local Transform Matrices**
   - Immediately following the basic bone information. Each bone occupies 64 bytes (Total: `BoneCount * 64` bytes).
   - The data is a 4x4 single-precision float matrix, column-major.
3. **Absolute Transform Matrices**
   - Immediately following the local matrices. Each bone also occupies 64 bytes.
   - **Core Design Detail**: For newer model versions (>= 190), the **global vertex scaling ratio** of the model is cleverly hidden in the absolute or local matrix of bone 0. By extracting the vector lengths of the first three columns of the matrix, the true scale multiplier that needs to be applied to the vertices can be reverse-calculated.
4. **Animation Bone Remap Table**
   - Immediately following the absolute matrices, the length is **fixed at 256 bytes**.
   - **Crucial Pitfall**: This is a lookup table used to map external animation tracks to the internal bone IDs. **It must NEVER be used as the bone mapping table for mesh vertices.** If mixed up in the code, it will cause vertex weights to be lost, resulting in catastrophic bugs like "meshes flying around" or "shattering in mid-air" when playing animations.

#### 1.3 Mesh Data Area
Located at `MeshOffset`. Each Mesh Header is **48 bytes** long.

| Offset | Type | Field Name | Description |
|---|---|---|---|
| `0x01` | uint8 | MeshType | Mesh type or rendering mode, e.g., visibility identifier. |
| `0x02` | uint16 | VertexCount | Number of vertices controlled by this mesh. |
| `0x05` | uint8 | MaterialIdx | Material ID, usually requires right-shifting by 4 bits (`>> 4`). |
| `0x08` | uint8 | SingleBone | **Single Bone Fallback ID**. When a mesh is determined to be a geometry without weights, all vertices are bound to this global bone by default. |
| `0x0A` | uint8 | Stride | **Vertex Stride** (number of bytes each vertex occupies), determining how the buffer is parsed. |
| `0x0B` | uint8 | BlockType | **Vertex Block Type**, used to distinguish internal data arrangement variants under the same stride (e.g., 196, 68, 4). |
| `0x0C` | uint32 | VertexSub | Vertex sub-offset multiplier. |
| `0x10` | uint32 | VtxOffsetAdd | Offset relative to the absolute vertex buffer offset. |
| `0x18` | uint32 | FaceOffset | Relative starting position of face index data (needs to be multiplied by 2 bytes to calculate true offset). |
| `0x1C` | uint32 | FaceCount | Number of face indices for this mesh. |
| `0x24` | uint8 | BoneMapIdx | Index for the local vertex-to-bone mapping table. Mostly deprecated in Switch compression formats. |

#### 1.4 Vertex Buffer Area
Absolute offset calculation formula: `VtxOffset + VtxOffsetAdd + (Stride * VertexSub)`.

Due to strict memory and performance requirements on hardware platforms, model vertices are compressed into extreme formats. All XYZ coordinates are usually stored as **16-bit signed short integers**, and parsing requires executing `Coordinate Value / 32767.0 * Global Scale + Offset` to restore them.

Below is an analysis of known specialized Stride formats (extremely important; lacking these parsing rules will cause skeletal skinning to shatter):

##### Format A: Multi-Weight Standard Format
*Used for the main character body or fine deformation parts*
- **Stride 40**:
  - `0x00-0x06`: XYZ coordinates (short)
  - `0x06-0x08`: Weight 1 (short, needs dividing by 32767.0)
  - `0x10-0x14`: Bone IDs 1 to 4 (four single bytes)
  - `0x14-0x18`: UV coordinates (Half-precision float)
  - `0x18-0x1C`: Weight 2 and Weight 3 (Half-precision float)
- **Stride 36**:
  - `0x10-0x14`: UV coordinates (Half-precision float)
  - `0x14-0x18`: Bone ID 1 and 2 (**stored as half-precision floats; must be decompressed and cast to integers**)

##### Format B: Highly Compressed Multi-Weight Format
*Removes redundant data like normals, while extremely compressing bones and weights*
- **Stride 28**:
  - `0x06-0x08`: Weight 1 (short)
  - `0x10-0x14`: Bone IDs 1 to 4 (four single bytes)
  - `0x14-0x18`: UV coordinates (Half-precision float)
  - `0x18-0x1C`: Weight 2 and Weight 3 (Half-precision float)
- **Stride 24**:
  - `0x06-0x08`: Weight 1 (short)
  - `0x10-0x14`: UV coordinates (Half-precision float)
  - `0x14-0x18`: Bone ID 1 and 2 (**hidden here, stored as half-precision floats**)

##### Format C: Single Bone Extreme Compression Format (e.g., Kushala Daora's torso scales)
*Triggered when `Stride = 20` and `BlockType = 68` or `4`.*
This format discards weights, and each vertex is **only controlled by a single unique bone (weight is fixed at 1.0)**.
- The engine plays a "trick": the ID of this single bone is **hidden directly at the end of the XYZ coordinates structure**!
- `0x00-0x06`: XYZ coordinates (short)
- `0x06-0x08` (i.e., the 7th and 8th bytes): **Local Bone ID (unsigned short)**.
- If these bytes are not extracted, the entire mesh will incorrectly fall back to the "Single Bone Fallback ID", causing meshes that originally relied on different bone deformations to become completely rigid and disjointed during animations.

### 2. Animation File Structure (.LMT)
This file is the crucial data managing skeletal animations.

#### 2.1 File Header Area
- `0x00` - `0x03`: File identifier, fixed as `LMT\x00`.
- `0x04` - `0x05`: Animation file version number.
- `0x06` - `0x07`: Total number of actions included.
- Starting from `0x08`: An array of unsigned 32-bit integers, storing the absolute file offset for each action's Anim Header.

#### 2.2 Anim Header (Action Info)
Located at the offset address calculated above.
- `0x00` - `0x03`: Starting offset for all "animation track" data included in this action.
- `0x04` - `0x07`: Total number of tracks (usually 256, corresponding to the 256-byte lookup table in the model file).
- `0x08` - `0x0B`: Total number of frames for this action.
- `0x0C` - `0x0F`: Starting frame of the animation loop, often used for looping gaits.

#### 2.3 Animation Tracks
Each track has a fixed length of 16 bytes, iterated according to the "Total number of tracks" mentioned above.
Each track corresponds to a virtual bone ID (requires mapping this virtual ID to a real bone using the lookup table in the model; e.g., if checking the table reveals track 3 maps to real bone 41, it means track 3 drives real bone 41).
Inside the track are absolute offsets to corresponding buffers:
- First uint32 (Offset + `0x00`): **Translation Buffer Offset**
- Second uint32 (Offset + `0x04`): **Rotation Buffer Offset**
- Third uint32 (Offset + `0x08`): **Scale Buffer Offset** (mostly 0, meaning no scaling deformation)

#### 2.4 Keyframe Buffer Decompression
The underlying engine uses highly complex floating-point difference and compression algorithms:
- **Extreme Value Limits**: The buffer header declares the maximum, minimum, and offset compensation for X, Y, and Z axes for that segment of motion.
- **Bit-Width Encoding**: Time frames are stored in either 1-byte or 2-byte depending on the compression mode; translations and rotations can be stored as 8-bit or 16-bit integers.
- **Restoring Interpolation**: The extracted 8-bit or 16-bit integers are used as interpolation factors to calculate a floating-point mapping within the range of the maximum and minimum values, ultimately restoring high-precision quaternions or spatial coordinates.

## 格式说明
*(以下内容由 Google Gemini 生成)*

### 1. 模型文件结构 (.MOD)
以 `version = 237` (Switch 版 MHGU) 为基准。文件结构严格按照小端序存储。

#### 1.1 文件头部区
总长度固定为 64 字节，定义了各数据块的位置与数量。

| 偏移量 | 长度 | 类型 | 字段名称 | 描述 |
|---|---|---|---|---|
| `0x00` | 4 | 字符数组 | Magic | 文件标识符，固定为 `MOD\x00` |
| `0x04` | 2 | 无符号16位整数 | Version | 主版本号 (MHGU 通常为 237) |
| `0x06` | 2 | 无符号16位整数 | Version2 | 次版本号 |
| `0x08` | 4 | 无符号32位整数 | BoneCount | 模型包含的骨骼总数 |
| `0x0C` | 4 | 无符号32位整数 | MeshCount | 模型包含的网格总数 |
| `0x10` | 4 | 无符号32位整数 | MaterialCount| 材质总数 |
| `0x14` | 4 | 无符号32位整数 | VertexCount | 全局顶点总数 |
| `0x18` | 4 | 无符号32位整数 | FaceCount | 全局面总数 (即索引数) |
| `0x1C` | 4 | 无符号32位整数 | EdgeCount | 边界或线框总数 |
| `0x20` | 4 | 无符号32位整数 | GroupCount | 节点或组总数 |
| `0x24` | 4 | 无符号32位整数 | BonesOffset | **骨骼数据区**的绝对偏移 |
| `0x28` | 4 | 无符号32位整数 | GroupOffset | **组数据区**的绝对偏移 |
| `0x2C` | 4 | 无符号32位整数 | TexOffset | **材质名称与资源区**的绝对偏移 |
| `0x30` | 4 | 无符号32位整数 | MeshOffset | **网格头部区**的绝对偏移 |
| `0x34` | 4 | 无符号32位整数 | VtxOffset | **顶点缓冲区**的绝对偏移 |
| `0x38` | 4 | 无符号32位整数 | FacesOffset | **面索引区**的绝对偏移 |
| `0x3C` | 4 | 无符号32位整数 | UnkOffset | 未知数据区或边界框数据偏移 |

#### 1.2 骨骼数据区
位于由骨骼区绝对偏移所指向的位置，包含三部分连续的数据块：

1. **骨骼基础信息**
   - 每个骨骼占 24 字节（总计 骨骼数 × 24 字节）。
   - `0x00`: 骨骼编号 (无符号8位整数)
   - `0x01`: 父骨骼编号 (无符号8位整数)，`255` 表示该骨骼为根节点，无父级。
   - `0x02`: 子骨骼编号 (无符号8位整数)
   - `0x03`: 状态标志或保留位 (无符号8位整数)
2. **局部变换矩阵**
   - 紧跟在骨骼基础信息之后。每个骨骼占 64 字节（总计 骨骼数 × 64 字节）。
   - 数据为 4x4 单精度浮点矩阵，列主序。
3. **绝对变换矩阵**
   - 紧跟在局部矩阵之后。每个骨骼同样占 64 字节。
   - **核心设计细节**：对于较新的模型版本（大于等于 190），模型的**全局顶点缩放比例**被巧妙地隐藏在第 0 号骨骼的绝对矩阵或局部矩阵中。通过提取矩阵前三列的向量长度，可以逆向计算出顶点需要乘上的真实缩放倍率。
4. **动画骨骼映射表**
   - 紧跟在绝对矩阵后，长度**固定为 256 字节**。
   - **极易犯错的避坑点**：这是用来将外部动画轨道映射到本体骨骼编号上的对照表，**绝对不能将其当作网格顶点的骨骼映射表**。在代码中如果混用，将导致顶点权重丢失，并在播放动画时发生“网格乱飞”、“碎裂在半空中”的毁灭性错误。

#### 1.3 网格数据区
位于网格绝对偏移处。每个网格头部长度为 **48 字节**。

| 偏移量 | 类型 | 字段名称 | 描述 |
|---|---|---|---|
| `0x01` | 无符号8位整数 | MeshType | 网格类型或渲染模式，如可见性标识。 |
| `0x02` | 无符号16位整数 | VertexCount | 此网格控制的顶点数量。 |
| `0x05` | 无符号8位整数 | MaterialIdx | 材质编号，通常需要右移 4 位取值。 |
| `0x08` | 无符号8位整数 | SingleBone | **单骨骼回退编号**。当网格被判定为无权重几何体时，所有顶点默认绑定到此全局骨骼。 |
| `0x0A` | 无符号8位整数 | Stride | **顶点步长** (每个顶点占用的字节数)，决定了缓冲的解析方案。 |
| `0x0B` | 无符号8位整数 | BlockType | **顶点块类型**，用于区分同样步长下的内部数据排列变体 (如 196, 68, 4)。 |
| `0x0C` | 无符号32位整数 | VertexSub | 顶点子偏移系数。 |
| `0x10` | 无符号32位整数 | VtxOffsetAdd| 相对顶点缓冲区的偏移量。 |
| `0x18` | 无符号32位整数 | FaceOffset | 面索引数据的相对起始位置 (读取时需乘以 2 字节计算真实偏移)。 |
| `0x1C` | 无符号32位整数 | FaceCount | 该网格的面索引数。 |
| `0x24` | 无符号8位整数 | BoneMapIdx | 局部顶点骨骼映射表的索引。在 Switch 等压缩格式中多废弃不用。 |

#### 1.4 顶点缓冲区
绝对偏移计算公式：`顶点缓冲绝对偏移 + 相对偏移量 + (步长 × 子偏移系数)`。

由于硬件平台对内存和性能的苛刻要求，模型的顶点被压缩成了极端的形态。所有的 XYZ 坐标通常存储为 **16 位有符号短整数**，解析时需要执行 `坐标值 / 32767.0 × 全局缩放 + 偏移量` 才能还原。

以下是已知特异化步长格式的剖析（极为重要，缺乏这些解析会导致骨骼蒙皮碎裂失效）：

##### 格式 A：多权重标准格式
*用于角色本体或精细形变部位*
- **步长 40**:
  - `0x00-0x06`: XYZ 坐标 (短整数)
  - `0x06-0x08`: 权重 1 (短整数，需除以 32767.0)
  - `0x10-0x14`: 骨骼编号 1 至 4 (四个单字节)
  - `0x14-0x18`: UV 坐标 (半精度浮点)
  - `0x18-0x1C`: 权重 2 与 权重 3 (半精度浮点)
- **步长 36**:
  - `0x10-0x14`: UV 坐标 (半精度浮点)
  - `0x14-0x18`: 骨骼编号 1 与 2 (**存储为半精度浮点，必须解压后转为整数**)

##### 格式 B：高压缩多权重格式
*将法线等冗余数据剔除，同时将骨骼和权重极度压缩*
- **步长 28**:
  - `0x06-0x08`: 权重 1 (短整数)
  - `0x10-0x14`: 骨骼编号 1 至 4 (四个单字节)
  - `0x14-0x18`: UV 坐标 (半精度浮点)
  - `0x18-0x1C`: 权重 2 与 权重 3 (半精度浮点)
- **步长 24**:
  - `0x06-0x08`: 权重 1 (短整数)
  - `0x10-0x14`: UV 坐标 (半精度浮点)
  - `0x14-0x18`: 骨骼编号 1 与 2 (**隐藏在此处，存储为半精度浮点**)

##### 格式 C：单骨骼极端压缩格式 (如钢龙的躯干鳞片)
*当遇到 步长 = 20 且 顶点块类型 = 68 或 4 时触发。*
这种格式抛弃了权重，每个顶点**仅受唯一一根骨骼控制 (权重固定为 1.0)**。
- 引擎玩了一个“把戏”：把这一根骨骼的编号，**直接藏进了表示 XYZ 坐标结构体的末尾**！
- `0x00-0x06`: XYZ 坐标 (短整数)
- `0x06-0x08` (即第 7 和第 8 个字节): **局部骨骼编号 (无符号短整数)**。
- 如果不提取这个字节，整个网格会被错误地回退到“单骨骼回退编号”上，从而导致原本依赖不同骨骼形变的网格完全僵死、在动画中分散错位。

### 2. 动画文件结构 (.LMT)
该文件是管理骨骼动画的关键数据。

#### 2.1 文件头部区
- `0x00` - `0x03`: 文件标识符，固定为 `LMT\x00`。
- `0x04` - `0x05`: 动画文件版本号。
- `0x06` - `0x07`: 包含的动作数量。
- `0x08` 开始: 一组无符号32位整数数组，存放着每一个动作信息头的绝对文件偏移量。

#### 2.2 动作信息头
位于上述计算得出的偏移地址。
- `0x00` - `0x03`: 此动作包含的所有“动画轨道”数据起始偏移。
- `0x04` - `0x07`: 轨道总数（通常是 256，对应模型文件中那张 256 字节的对照表）。
- `0x08` - `0x0B`: 此动作的总帧数。
- `0x0C` - `0x0F`: 动画循环的起始帧，常用于循环步态。

#### 2.3 动画轨道
每条轨道固定长度 16 字节，对应上述的“轨道总数”进行遍历。
每一个轨道对应一个虚拟的骨骼编号（需要通过模型里的对照表将该虚拟编号映射到真实骨骼，例如查表得出第 3 条轨道映射到真实的 41 号骨骼，则代表第 3 条轨道驱动的是真实骨骼 41）。
轨道内部存有对应缓冲区的绝对偏移量：
- 首个无符号32位整数 (偏移量 + `0x00`): **位移缓冲区偏移**
- 第二个无符号32位整数 (偏移量 + `0x04`): **旋转缓冲区偏移**
- 第三个无符号32位整数 (偏移量 + `0x08`): **缩简缓冲区偏移** (大多为 0，代表不发生形变缩放)

#### 2.4 关键帧缓冲解压
底层引擎使用了高度复杂的浮点数差分和压缩算法：
- **极值限制**: 缓冲区头部会声明该段动作在 X, Y, Z 三个轴上的最大值、最小值以及偏移补偿。
- **位宽编码**: 时间帧根据压缩模式的不同，可能是单字节或者双字节存储；位移和旋转可能是 8 位或 16 位整数存储。
- **还原插值**: 提取出的 8 位或 16 位整数需要作为插值因子，在最大值与最小值的范围内进行浮点映射计算，最终还原出高精度的四元数或空间坐标。
